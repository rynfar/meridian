# #1476 review record — Pi's cache-only model refresh phase

- PR: [#1476](https://github.com/rynfar/meridian/pull/1476) by Nate Berkopec, "fix: honor Pi's cache-only model refresh phase".
- Reviewed base `origin/main` `4d16958af18abcba807941a3028f25cf3f03782b`; contributor head `ef3ac97ef0dd7b18de92732fbd65faafab3fdd3e` (three unsigned commits). No maintainer commits.
- Disposition: **deferred for an owner design decision.**

The change follows Pi's documented contract (`allowNetwork` is false during offline/cache-only initialization) and removes a startup wait of up to about 3.5 s. That wait needs both no usable stored catalog and a Meridian that accepts the connection but never replies. The code it deletes is a deliberate decision recorded in the comment on main: "without it a first `pi -p --model meridian/…` would find no models."

## Review findings

1. **High: silent fallback to Pi's direct Anthropic provider.** With docs/agents.md's recommended `"defaultProvider": "meridian"`, no usable catalog and an Anthropic key configured, the head starts on `anthropic/claude-opus-4-8` in 8/8 runs across Pi 1.3.0 and 1.4.0, and stays there after the catalog arrives. Main picks `meridian/claude-haiku-5-5` in 18/20 runs (the two misses are an existing Pi race). Traffic would bypass Meridian without a message.
2. **High: `--model meridian/…` without a usable catalog exits 1 with `Model "meridian/…" not found`** in print, RPC and interactive mode (interactive tested under a pty) on both Pi versions; main works in each. A catalog is unusable when missing, older than 7 days (`STORED_CATALOG_TTL_MS`) or saved for another Meridian URL. This breaks the documented quick-start (`meridian setup --client pi` then `pi --model meridian/claude-sonnet-5-5`) on every fresh install, ephemeral CI always, and print-only machines a week after their last interactive or RPC session. `pi update --models` reports success but does not load extensions, and `meridian setup --client pi` never contacts Meridian, so there is no non-interactive way to fill the catalog. The PR and its SPEC note describe this as only a cold non-interactive case.
3. **Medium: a committed gate breaks.** `scripts/e2e-pi-extension-side-calls.mjs` starts `pi --mode rpc --model meridian/claude-haiku-5-5` with an empty catalog; it fails at startup on the head on both Pi versions and passes on main.
4. **Medium: docs would be stale** — docs/agents.md quick-start and known limits, the SPEC wording, and E2E.md's Pi section (it says the real-model harness asserts discovery; it now checks its own priming call; the new `scripts/e2e-pi-startup.mjs` is not listed).
5. **The fixed problem is narrow:** with Meridian down (connection refused) main already started in 398–483 ms (head 347–416 ms); a fresh catalog already skipped the fetch; main's failure in the contributor's startup harness is not reliable on Pi 1.4.0 (4/6 runs, 3398–3691 ms) because of a Pi race, 3/3 on Pi 1.3.0; the head passed 10/10.
6. Checked and correct: Pi 1.3.0 and 1.4.0 behave the same (network refresh only in RPC after ready, interactive after the UI starts, and `/model`; never in print mode); the new early return covers the removed `PI_OFFLINE` check; error propagation is effectively unchanged; the updated unit tests catch the old behavior; the real-model harness's catalog priming is correct and required on the head.

A healthy fresh Meridian answered the first `/v1/models` in 199 ms.
- Not run: resuming a saved `meridian/…` session (`pi -c`), read from Pi's code only.

## Options for the owner

1. **Strict (this PR):** accept findings 1–2, then correct the side-calls harness and the docs, and warn that `defaultProvider: meridian` can silently fall back.
2. **Bounded fetch (reviewer's recommendation):** keep main's cold-start fetch when nothing usable is stored, including its `PI_OFFLINE` check, with a short (about 1 s) timeout during startup. A healthy Meridian answers in about 200 ms, so cold starts keep working, and the stuck-Meridian wait drops from about 3.4 s to about 1.4 s. The contributor's startup harness and tests can stay, adjusted. This replaces most of the PR's change, so it should go to the contributor first.
3. **Decline:** keep main as is.
