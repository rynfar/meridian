## The problem and the first review

Pi calls `refreshModels` with `allowNetwork: false` at startup; its contract calls that phase cache-only. On main the extension fetched `/v1/models` there whenever no usable stored catalog existed, so a Meridian that accepted connections but never replied held Pi's startup for 3.4–3.9 s. The PR stopped that fetch. Real Pi 1.4.0 and 1.3.0 then showed that the cache-only phase answered with nothing whenever no usable catalog was stored: on a fresh install, after the 7-day TTL, or for a new `MERIDIAN_BASE_URL`.

- `--model meridian/…` exited `Model "meridian/…" not found` in print, RPC and interactive mode. That included the documented first run after `meridian setup --client pi`.
- Print mode never refreshes, so it never recovered.
- With a `defaultProvider`/`defaultModel` naming a Meridian model and an Anthropic credential configured, Pi started silently on its own `anthropic/…` provider.
- `scripts/e2e-pi-extension-side-calls.mjs` failed at startup.
- `pi update --models` does not load extensions, and setup never contacts Meridian, so nothing could fill the catalog without an interactive or RPC session.

## Decision

The owner chose the correct design over a bounded (timeout) fetch:
- Pi's contract is honored exactly: no network in the cache-only phase.
- The cause of the empty answer is removed, rather than shortening the wait.

A bounded fetch would still have broken the contract, depended on a timeout, and could fail for a Meridian on another machine.

The cache-only answer (`cacheOnlyModels`, `plugin/pi/catalog.ts`) is never empty:
1. The catalog last discovered from the same URL, while it is fresh (7 days).
2. Once it has expired, the same catalog, but only while it still lists every built-in model. A catalog lacking one usually predates the Meridian version that ran setup. So an upgrade's new models reach print mode once the old catalog expires.
3. Otherwise a built-in catalog of the models this Meridian version serves. It mirrors `buildModelList(false)`, and a test keeps the two identical. The plugin may not import server code.

Only discovered catalogs are persisted. A discovery that lists no usable Claude models counts as a failure, like any other: the extension falls back to a fresh stored catalog, or throws so that Pi records the error and keeps the list it already published.

`plugin/SPEC.md` records the decision and its limits:
- Until a discovery succeeds, the built-in catalog shows Opus 4.6 at 200k even with the legacy 1M entitlement, and 1M windows even under the 1M opt-out.
- A Meridian of another version at the URL can differ from the built-in catalog, and the coverage test can misjudge such a catalog.
- Pi refreshes a running session's model only when a provider is registered.

`docs/agents.md` was updated, and its migration step now names `defaultModel`: Pi's `findInitialModel` ignores `defaultProvider` without it.
