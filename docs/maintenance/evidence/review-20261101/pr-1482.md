## Review findings

1. **Fixed: PDFs from earlier turns vanished from packed history.**
   - The PR changed `extractOpenAiContent`, which handles only system messages. Packed history for unkeyed clients is built by `summarizeAnthropicContent`, which had no `document` case.
   - On the follow-up turn the history read as if no document had ever been attached. Images in the same position show `[Image attached]`.
   - Now `[Document attached]`.
2. **Fixed: the new catch-all mislabelled OpenAI's assistant `refusal` part.** A replayed refusal became an "unsupported part" note inside the assistant's own turn; it now keeps the refusal text.
3. **Fixed: docs and spec.**
   - `docs/agents.md` now documents file parts and the packed-history placeholders.
   - `src/proxy/SPEC.md` records the decision that an undeliverable part becomes a visible omission note, never a silent drop.
4. **Accepted shapes.** The openai-node type and OpenAI's file-inputs guide say Chat Completions supports only `application/pdf`, for both `file_data` and `file_id`.
   - Accepted: PDF data URLs, case-insensitive MIME.
   - Given a visible note: `file_id`, non-PDF data, raw base64 without the prefix, and data URLs with parameters.
   - Nothing that failed silently before is silent now. A message whose only part was a file used to go upstream as `content: []`.
5. **Consistent with the existing paths.** The PR uses the same `parseDataUrlPdf` and document shape as the Responses `input_file` path. Downstream it treats documents exactly as images, including inside `tool_result`.
6. **Owner decisions:** the owner accepted the reviewer's recommendations, all of which keep existing behavior:
   - keep the visible note for unknown parts;
   - keep placeholders rather than 400s for undeliverable attachments;
   - make carrying earlier media forward in packed conversations a follow-up;
   - defer raw-base64 support until a client sends it.
