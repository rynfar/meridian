# #1340 replay guard: never return a replayed result as fresh (2026-10-13)

## Review finding addressed

The maintainer disposition of `ab836ac7` used this negative control. A status poll `read({path})` returned
`running`. After a backend replacement, the next identical read was legitimate, but the guard answered it with the
recorded `running` instead of dispatching it. Name and arguments do not identify an operation.

## Change

In a replayed run, before any call has been sent to the client, the first request identical to a completed tail
call is not executed. It gets a not-executed notice (`is_error`) that names the delivered `tool_use_id` whose result
is already in the history, and it carries no client content. Repeating the call after the notice dispatches it to
the client. `completedToolTail` keeps only delivered ids, not results.

This is not exactly-once. A model can repeat through another tool, or repeat on purpose after the notice.

## Deterministic negative control

`src/__tests__/antigravity-replay-duplicate.test.ts`, test "a polled status is read fresh, never answered stale".
The history holds a `read` that returned `running`; the fixture model reads the same path twice after the replay.

| Source | Result |
| --- | --- |
| `ab836ac7` guard (with current main) | `REPLAYED:running\|done`: the stale value was returned as the first read |
| this revision | `REPLAYED:<notice>\|done`: the second read reached the client as `tool_use` |

## Live: actual Pi + Meridian Pi integration + official agy 1.2.7, macOS arm64

The harness is `scripts/e2e-antigravity-replay-poll.mjs`. It follows the structure of
`e2e-antigravity-idle-conversation.mjs`:

- It pins the official agy 1.2.7 executable and sets `AGY_CLI_DISABLE_AUTO_UPDATE=true`.
- It runs actual Pi in RPC mode with the real `dist/antigravity-clients/pi.js` integration. Before any model call,
  it verifies that integration against a local fixture (`meridian_request_id`).
- It scrubs provider environment variables and uses a local service key.
- It requires every original child process and its pipes to close.
- It checks that the executable hash is unchanged afterwards.
- It writes its report with `wx`.

The scenario: Pi polls a status file that says `running`. After Pi's first read completes, the relay changes the
file to `done` and replaces the backend before forwarding that result, so the next request is a completed-history
replay. The harness then reads the replayed native conversation's own CLI transcript and records what the client
MCP bridge returned to the model. The gate fails if `running` was returned there.

The model's repeated read happened in every guarded arm. With the previous guard, the replayed conversation
received the recorded `running` after the file had already changed to `done`; the model only recovered because it
read once more. With this revision it received the notice, its next read reached Pi, and it got `done`. In the CLI
transcript, each notice appears twice for one guard event (`guardEvents` 1).

The documented recovery gate also passed with this revision on the same agy 1.2.7, using
`E2E_AGY_RECOVERY=1 E2E_CLIENT=pi node scripts/e2e-antigravity-clients.mjs`. It passed all 12 checks, including
"backend restart between client tool execution and result delivery; no repeated completed tool"
([`recovery-candidate.json`](1340-replay-notice-20261013/recovery-candidate.json)).

### Retained failed attempts

- An earlier attempt used agy 1.3.3 from the install script, which only serves the latest CLI, with a local
  version-gate edit. Those runs are not counted.
- The first pinned attempt passed Pi's library entry point `dist/cli.js` instead of the package `bin`
  (`dist/bundle/cli.js`). Pi exited before `get_state` in every arm, with no model call, so those runs are not
  counted.

## Not covered
